# Configuration

This guide is for operators configuring benchmark runs. Candidate-facing tool
instructions are generated by the runner in `CANDIDATE_ENVIRONMENT.md`.

Start from [`configs/run.example.json`](../configs/run.example.json).
`configs/opencode.json` supplies the tool-permission baseline. Run configuration
fields below belong to this runner; provider options are translated by OpenCode
and its selected provider adapter.

## Model connection and reasoning

| Field | Meaning |
| --- | --- |
| `backend` | `opencode` for a model run; `local-smoke` for the synthetic local test |
| `harness_executable` | OpenCode executable; supported adapter version: `1.18.17` |
| `model_id` | OpenCode `provider/model` identifier |
| `provider_configuration` | OpenCode provider registrations, connection settings, and model metadata |
| `credential_env` | Environment variable names forwarded to OpenCode, never to computation containers |
| `reasoning_effort` | Reported reasoning setting for the attempt |
| `harness_variant` | The variant selected through OpenCode `--variant` |
| `harness_variant_options` | Provider-specific options registered under that variant |
| `round` | Positive integer identifying an independent run |

Register the connection and model under `provider_configuration`, following the
provider adapter's configuration for the installed OpenCode version. Use an
environment reference such as `{env:OPENAI_API_KEY}` for the provider's
`options.apiKey`. Include that environment variable's name in `credential_env`.
See [usage](usage.md#3-configure-and-run-a-model) for the credential setup steps.

Set the provider's reasoning options in `harness_variant_options` and select
them with `harness_variant`. Record the intended effort in `reasoning_effort`.
The runner checks this label against `reasoningEffort` or `output_config.effort`
when present. Use the parameter format supported by your provider.

### Image input

For a custom vision-capable model, declare image input in its registration.
OpenCode 1.18.17 inherits capabilities for known models; new custom models
without inherited metadata default to image input disabled. Use native `read`
to open image files; registration controls whether OpenCode forwards the images
to the model.

Add the following model metadata under this runner's `provider_configuration`,
using the provider and model identifiers from `model_id`:

```json
{
  "provider_configuration": {
    "your-provider": {
      "models": {
        "your-model": {
          "modalities": {
            "input": ["text", "image"],
            "output": ["text"]
          }
        }
      }
    }
  }
}
```

Merge this fragment into your provider connection configuration when the model
and endpoint support images. For a text-only endpoint, use `["text"]` instead.
Include an image-reading check in your initial connection test.

OpenCode 1.18.17 references: [custom providers](https://github.com/anomalyco/opencode/blob/v1.18.17/packages/web/src/content/docs/providers.mdx#custom-provider),
[image capability defaults](https://github.com/anomalyco/opencode/blob/v1.18.17/packages/opencode/src/provider/provider.ts#L1374),
and [image handling](https://github.com/anomalyco/opencode/blob/v1.18.17/packages/opencode/src/provider/transform.ts#L405).

## Output-token limits

| Field | Applied setting |
| --- | --- |
| `harness_output_token_cap` | `OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX` in the OpenCode process environment; `null` leaves it unset |
| `model_output_token_limit` | `provider.<provider>.models.<model>.limit.output`; `null` leaves the registration unchanged |

Leave both fields `null` to use OpenCode and provider defaults. OpenCode 1.18.17
uses **32000 tokens per generation request** as its default ceiling. Its standard
calculation takes the smaller of this ceiling and a positive registered model
output limit, falling back to 32000 when that limit is unset or zero. For example,
a registered limit of 16384 gives 16384; 65536 gives 32000 unless the harness cap
is also raised. Provider limits may further restrict the allowance. See the
[limit function](https://github.com/anomalyco/opencode/blob/v1.18.17/packages/opencode/src/provider/transform.ts#L1330)
and [request preparation](https://github.com/anomalyco/opencode/blob/v1.18.17/packages/opencode/src/session/llm/request.ts#L119).

Choose values supported by the tested model and keep them consistent across
compared runs. Reasoning-token accounting follows the provider's API.

The Bash adapter's separate 120000-character display limit only truncates tool
output shown to the model. It does not change the token cap or delete saved data.

## Command timeout and total task time

`command_timeout_max_seconds` is **1200 seconds in the example configuration**.
Adjust it to the task's computation duration and use the same policy for
comparable runs.

`timeout` is an argument supplied by the candidate when calling Bash, not a
run-configuration field.

There are three distinct time limits:

| Setting | Unit | Meaning |
| --- | --- | --- |
| Bash tool argument `timeout` | Milliseconds | Requested duration of one tool call; omitted value defaults to `120000` (120 seconds) |
| `command_timeout_max_seconds` | Seconds | Configured maximum for one Bash call; example: `1200` |
| `time_limit_minutes` | Minutes | Overall task deadline from `resource_limits.json`; converted to seconds by the runner |

A call is bounded by the requested duration (or its default), the configured
single-command maximum, and the remaining task time. A longer computation needs
an explicit longer tool timeout within those limits. The overall task deadline
still applies. This runner setting requires a positive integer; the candidate
instructions state both the default and configured maximum.

## File-tool paths

The runner explains the two workspace paths to the candidate in
`CANDIDATE_ENVIRONMENT.md`. Bash runs in the computation container at `/workspace`;
native `read`, `write`, and `edit` tools run on the host and use the absolute host
workspace path printed there. For example, the host's
`<absolute-workspace>/submission/code.py` is the same file as
`/workspace/submission/code.py` in Bash. Candidate instructions direct native file
tools to the host path and Bash to the container path.

The permission baseline allows `read` and `edit`. OpenCode's native `write` and
`apply_patch` tools use the `edit` permission, as shown in its
[write implementation](https://github.com/anomalyco/opencode/blob/v1.18.17/packages/opencode/src/tool/write.ts).
Only the workspace is mounted for candidate computation. Final files
belong in `submission/`, and intermediate files in `scratch/`. Model credentials
are not mounted into the container.

## Resource limits and isolation

`resource_limits.json` uses the dataset's fields:

| Field | Meaning |
| --- | --- |
| `nodes` | `1` for this single-node runner |
| `cpu_cores` | Positive CPU allocation; also used for numerical-library thread settings |
| `time_limit_minutes` | Total candidate work time in minutes, including preparing final files |
| `network_access` | Must be `disabled` for candidate computation |
| `temporary_storage_gib` | Temporary disk allowance in GiB to enforce on the host; 1 GiB = 2^30 bytes |
| `available_memory_gib` | Approximate available RAM, where supplied; not an enforced limit |
| `memory_policy` | Task-specific memory guidance, when supplied |

The runner enforces the work deadline and stops containers before archiving.
Allow collection time in the scheduler allocation separately from candidate work
time. Configure CPU allocation and scratch quotas through the host resource manager.

| Run configuration field | Meaning |
| --- | --- |
| `container_runtime` | Podman executable or a compatible deployment wrapper |
| `container_image` | Scientific image reference pinned with `@sha256:<digest>` |
| `task_only_deployment_confirmed` | Set to `true` only after preparing a host without evaluator materials, previous answers, or unrelated secrets |
| `resource_limits_enforced_externally` | Set to `true` only after the task's CPU and scratch limits are enforced |

The confirmation flags record the host preparation described above. Computation
runs offline with a read-only root filesystem and task-input mount. Model
credentials and endpoint access belong to the OpenCode process on the host.

## Submission export

| Field | Example | Meaning |
| --- | --- | --- |
| `submission_max_files` | `10000` | Export file-count threshold |
| `submission_max_bytes` | `2147483648` | Export size threshold (2 GiB), separate from scratch space |
| `submission_overflow_policy` | `warn_and_seal` | Warn and retain all regular submission files above thresholds; `reject` opts into hard rejection |

Missing required submission files are reported without blocking partial-result
collection. Symbolic links, changing files, and detected credential values are
rejected during export.
